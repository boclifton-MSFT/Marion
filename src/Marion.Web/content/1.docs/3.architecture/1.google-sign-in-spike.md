## Decision

Implement Google authentication as a **Nitro-only OpenID Connect authorization-code flow**. Use [`openid-client`](https://github.com/panva/openid-client) for discovery, S256 PKCE, authorization-code exchange, and ID-token validation. Use H3's sealed server-session helpers only for opaque-cookie mechanics; do **not** use a generic Google/OIDC handler as the authentication verifier.

This boundary is deliberate: the OIDC library owns protocol security; the session library owns sealed-cookie mechanics. The browser only navigates to Marion routes and never receives a client secret, authorization code, ID token, access token, refresh token, or PKCE verifier.

Google's [OIDC guidance](https://developers.google.com/identity/openid-connect/openid-connect) requires an exact redirect URI, state verification, and validation before trusting claims. The [OIDC Core code flow](https://openid.net/specs/openid-connect-core-1_0.html#CodeFlowAuth) is the protocol baseline.

## Current evidence and endpoint decision

`src/Marion.AppHost/AppHost.cs` currently registers `frontend` with `AddViteApp`, `.WithHttpEndpoint(env: "PORT")`, and `.WithExternalHttpEndpoints()` (lines 46-50). With no explicit host port, Aspire assigns the browser-facing port dynamically. `NUXT_API_BASE` is supplied only to the Nuxt server at line 52; it is not a browser callback URL. Therefore the current endpoint cannot be registered reproducibly with Google.

Adopt **`https://localhost:7257`** as the stable local browser origin. The follow-on implementation must update the existing Vite `http` endpoint to fixed port `7257` and opt it into Aspire's HTTPS developer certificate (rather than add a second Vite endpoint), conceptually:

```csharp
.WithHttpEndpoint(port: 7257, env: "PORT")
.WithHttpsDeveloperCertificate()
.WithExternalHttpEndpoints()
```

`AddViteApp` owns one endpoint and changes that endpoint to HTTPS when the developer certificate is enabled. Aspire's [networking model](https://aspire.dev/fundamentals/networking-overview/) confirms that a fixed host port is the stable proxy address while the JavaScript process may retain a dynamic target port.

### Google Cloud Console values

Create a separate **Web application** OAuth client for each environment.

| Console field | Local development | Production |
| --- | --- | --- |
| Application type | `Web application` | `Web application` |
| Name | `Marion local` | `Marion production` |
| Authorized JavaScript origin | `https://localhost:7257` | `https://<app-domain>` |
| Authorized redirect URI | `https://localhost:7257/auth/google/callback` | `https://<app-domain>/auth/google/callback` |
| Requested scopes | `openid email profile` | `openid email profile` |

The server code flow does not require Google Identity Services in browser JavaScript, so the origin is not used by the flow itself; keep it limited to the same origin and do not add wildcard origins. Configure production consent-screen branding, support contacts, and the verified `<app-domain>` before production registration. Do not share a production client secret with local development.

### Required runtime validation

The dynamic-port conclusion above is verified from the current AppHost source. The fixed HTTPS endpoint, trusted certificate, and actual callback cannot be proven until the follow-on changes exist. Before Google registration is considered complete, run:

```powershell [Terminal]
aspire start --non-interactive
aspire wait frontend
aspire describe frontend
```

Confirm the reported browser URL is exactly `https://localhost:7257`, navigate the complete Google flow, and confirm the callback is accepted without a TLS or `redirect_uri_mismatch` error. If the development certificate is not trusted, trust it through the approved Aspire certificate workflow before testing. Re-run these commands after any AppHost endpoint change.

Do not use `aspire start --isolated` for Google callback registration validation: isolated mode deliberately randomizes resource ports so parallel worktrees cannot collide. Use the ordinary local AppHost run above when validating the registered stable callback origin.

## Routes and flow

These server routes live under `src/Marion.Web/server/routes/auth/`, outside the existing `src/Marion.Web/server/api/[...path].ts` upstream proxy:

| Route | Behavior |
| --- | --- |
| `GET /auth/google` | Accepts an optional allowed local `returnTo`, creates a one-time transaction, then redirects to Google's discovered authorization endpoint. |
| `GET /auth/google/callback` | Consumes and validates the transaction, exchanges the code server-side, validates the ID token, creates a Marion session, then redirects to the saved allowed path. |
| `POST /auth/logout` | Revokes the Marion session by clearing it; it does not call Google or retain provider tokens. |

The login and signup Google buttons in `app/pages/login.vue` and `app/pages/signup.vue` are currently toasts. Replace them with normal browser navigation to `/auth/google` (not `useApi()` and not a request through `/api/[...path]`).

For each start request, generate cryptographically random `state`, `nonce`, and PKCE verifier; send `response_type=code`, the derived S256 challenge, and `code_challenge_method=S256`. Do not request `access_type=offline`. Seal the verifier, state, nonce, validated relative return path, issue time, and a transaction identifier in a one-use `__Host-marion_oauth_tx` cookie. It must be `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, have no `Domain`, and expire in five minutes. Consume it before the token exchange; reject missing, expired, replayed, or mismatched state.

At the callback, `openid-client` must use Google's discovery metadata and JWKS, perform the code exchange only on the server, and validate the ID token's signature, issuer, audience (and `azp` where applicable), `exp`, bounded `iat`, and nonce. A decoded JWT is not an authenticated identity. Do not fall back to an unvalidated decode; an authenticated UserInfo response is only an acceptable alternative if its `sub` is checked against the validated token identity.

## Configuration and secrets

Add only private Nuxt runtime configuration:

| Runtime config path | Environment variable | Required value |
| --- | --- | --- |
| `oauth.oidc.issuer` | `NUXT_OAUTH_OIDC_ISSUER` | `https://accounts.google.com` |
| `oauth.oidc.clientId` | `NUXT_OAUTH_OIDC_CLIENT_ID` | Environment-specific Google client ID |
| `oauth.oidc.clientSecret` | `NUXT_OAUTH_OIDC_CLIENT_SECRET` | Environment-specific Google client secret |
| `oauth.oidc.redirectUri` | `NUXT_OAUTH_OIDC_REDIRECT_URI` | The exact callback URI in the table above |
| `auth.session.password` | `NUXT_SESSION_PASSWORD` | Unique random secret of at least 32 characters |
| `authStore.connectionString` | `NUXT_AUTH_STORE_CONNECTION_STRING` | Private connection to the shared Marion SQL database |
| `authStore.provisionSchema` | `NUXT_AUTH_STORE_PROVISION_SCHEMA` | `true` only for controlled local/schema-provisioning runs |

Keep those paths outside `runtimeConfig.public`; Nuxt exposes only keys in that public section. H3 uses `NUXT_SESSION_PASSWORD` to seal session data. The current `.env.example` has legacy `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` placeholders; the implementation must replace those placeholders with the names above, without adding values.

Store local values only in the developer's ignored `.env` or user-secret mechanism. Store deployed values in the deployment platform's secret store and inject them as environment variables. Never commit, log, trace, return, or put in browser configuration any client secret, session password, authorization code, verifier, token, cookie value, email address, or Google `sub`. Telemetry must redact those fields.

## Marion session and identity boundary

Configure the sealed, browser-opaque session cookie as `__Host-marion_session; Secure; HttpOnly; SameSite=Lax; Path=/` with no `Domain`. Store only a Marion internal subject/session identifier and issuance/activity timestamps—never Google tokens or profile data. Require a 30-minute idle limit and an 8-hour absolute limit in server-side session validation, rotate the session on successful login, and clear/revoke it on logout. H3 sealed sessions provide only cookie mechanics; the durable repository remains the authority for expiry, rotation, and revocation.

Google identity stops at an immutable external-identity boundary:

```text
(issuer = "https://accounts.google.com", subject = validated ID-token sub)
    -> Marion internal user/session identifier
```

Make `(issuer, subject)` the unique external identity key. Google documents `sub` as immutable and explicitly says email can change; email, `email_verified`, name, and picture are mutable profile attributes only. Do not key, join, authorize, or deduplicate users by email. This spike does not choose a borrower, tenant, role, or data-ownership model.

### Durable authentication-store contract

Nitro's default process-local storage is not valid for authentication state. Authorization transactions, sessions, and external identities use the shared `mariondb` SQL store. Transaction replay prevention is a conditional SQL delete, session rotation is one database transaction, revocation is a delete, session activity uses compare-and-set, and `(issuer, sub)` resolution uses a serializable key-range lock and primary key.

For local Aspire development, the frontend receives the logical `mariondb` connection only as a server-process environment variable, waits for the database, and explicitly enables local schema provisioning. Local runs must use the persistent Aspire SQL volume; running Nuxt without a configured shared store fails sign-in closed.

For production, an operator must provide `NUXT_AUTH_STORE_CONNECTION_STRING` through the deployment secret mechanism for a shared transactional SQL Server/Azure SQL database, provision the three `MarionAuth*`/`MarionExternalIdentities` tables in a controlled one-time migration or provisioning run, then leave `NUXT_AUTH_STORE_PROVISION_SCHEMA` disabled for runtime replicas. The database principal needs only the table DDL permission during provisioning and transactional CRUD permission at runtime. Never substitute Nitro memory storage, local files, or per-replica SQLite; those break replay, revocation, and identity guarantees under restart or horizontal scale.

## Public behavior and exclusions

`/`, `/pricing`, `/blog`, `/changelog`, and `/docs/**` remain anonymous. Do not introduce a global authentication redirect. A future protected route must use SSR server middleware that requires the Marion session; its route list and authorization policy are out of scope.

This spike excludes Entra authentication, password login, account linking, roles, multitenancy, borrower-data ownership, Google API authorization, offline access/refresh tokens, and provider-token persistence.

## Follow-on implementation issue

Implement the following as one deliverable:

1. Add the stable local HTTPS Aspire endpoint and the private configuration/session dependencies.
2. Add the three server routes, full `openid-client` code flow, sealed one-use transaction, sealed rotating session, and identity-resolution boundary.
3. Make the existing Google buttons use browser navigation and add protected-route middleware only when a protected route is introduced.
4. Add focused tests for:
   - S256 PKCE, state, nonce, five-minute one-use transaction, and safe `returnTo` validation;
   - rejected state/replay/error callback and rejected invalid issuer, signature, audience/`azp`, expiry, issue time, and nonce;
   - server-only exchange and absence of tokens/secrets in responses, browser runtime config, cookies, and telemetry;
   - required `__Host-marion_session` attributes, 30-minute idle/8-hour absolute expiry, login rotation, and logout clearing;
   - `(issuer, sub)` identity lookup without email as a key;
   - anonymous public routes and a session-required protected-route example; and
   - `aspire start --non-interactive`, `aspire wait frontend`, and `aspire describe frontend` proving `https://localhost:7257` before live Google callback validation.
